# Nasos: Arduino Nano + ESP32

## Важно: какая прошивка для какой архитектуры

- **`Osnova.ino`** — это **монолитный референс** (историческая базовая версия), где логика и I/O были в одном контроллере.
- Для **split-архитектуры (Nano + ESP32 по I2C)** использовать нужно только:
  - **Arduino Nano: `v1.ino`**
  - **ESP32: `esp32_controller.ino`**
- Прошивка `Osnova.ino` **не предназначена** для работы в split-архитектуре и не должна загружаться в Nano в этой связке.

## Роли контроллеров в split-архитектуре

1. **`v1.ino` (Arduino Nano, I/O bridge)**
   - читает уровни, аналоговые входы и давления;
   - управляет только реле скважинного насоса;
   - работает как I2C slave и отдает бинарную телеметрию ESP32.

2. **`esp32_controller.ino` (ESP32, master-логика + VFD Modbus RTU)**
   - основная логика двух насосов и защит;
   - веб-интерфейс/API;
   - управляет VFD по RS-485/Modbus RTU через `Serial2`;
   - формирует управляющие команды Nano по бинарному I2C протоколу.

3. **`data/index.html`**
   - веб-панель мониторинга и настройки.


## Подключение MAX485 к ESP32 (новая схема VFD)

VFD (Modbus RTU) теперь подключается к **ESP32**, а не к Nano.

- `ESP32 GPIO17 (TX2)` → `DI` (MAX485)
- `ESP32 GPIO16 (RX2)` ← `RO` (MAX485) **через делитель**:
  - `RO -> 10k -> ESP32 RX`
  - `ESP32 RX -> 20k -> GND`
- `RE` и `DE` объединены и идут на `ESP32 GPIO27`
  - `LOW` = приём
  - `HIGH` = передача
- Питание MAX485: `5V`

Это снижает нагрузку на Nano и повышает устойчивость связи VFD.

## Критично по проводке: A4/A5 заняты I2C

В split-архитектуре линии Nano:
- **A4 = SDA**
- **A5 = SCL**

Эти пины **зарезервированы под I2C** и не могут использоваться как входы уровней.

### Правильное назначение датчиков уровней в `v1.ino`

- `L1` → `D4`
- `L2` → `D5`
- `L3` → `A6`
- `L4` → `A7`

Если в старом монтаже `L1/L2` были заведены на `A4/A5`, их нужно **обязательно** перенести на `D4/D5`.


## Единая конфигурация I2C адреса и пинов

Чтобы исключить рассинхрон между прошивками, общий адрес и I2C-параметры вынесены в `i2c_link_config.h`:
- `i2cLinkCfg::NANO_SLAVE_ADDRESS` (по умолчанию `0x09`)
- `i2cLinkCfg::ESP32_SDA_PIN` / `i2cLinkCfg::ESP32_SCL_PIN`
- `i2cLinkCfg::BUS_FREQUENCY_HZ`

Изменять адрес нужно **только в этом файле**.

## Подключение Nano ↔ ESP32 (I2C)

- `Nano A4 (SDA)` ↔ `ESP32 GPIO21 (SDA)`
- `Nano A5 (SCL)` ↔ `ESP32 GPIO22 (SCL)`
- `GND Nano` ↔ `GND ESP32` (**общая земля обязательна**)

### Уровни напряжений (обязательно)

- ESP32 работает на **3.3V** и **не 5V-tolerant**.
- Nano обычно 5V.
- Между Nano и ESP32 по I2C нужен безопасный интерфейс:
  - двунаправленный I2C level shifter (типовой BSS138),
  - либо эквивалентная корректная схема согласования уровней.

## Мини-чеклист перед первым запуском

1. В Nano загружен **`v1.ino`**.
2. В ESP32 загружен **`esp32_controller.ino`**.
3. `A4/A5` на Nano используются только как SDA/SCL.
4. `L1/L2` действительно подключены к `D4/D5`.
5. Есть корректное согласование уровней 5V↔3.3V.
6. Земля Nano и ESP32 соединена.

## Ожидаемое failsafe-поведение при потере связи

Связь Nano↔ESP32 контролируется по бинарным кадрам команд/телеметрии.

- При потере свежей телеметрии или устойчивых ошибках обмена ESP32 переводит систему в безопасное состояние.
- Насосы останавливаются (реле и RUN-команда снимаются), чтобы исключить неконтролируемую работу.
- После восстановления устойчивой связи управление возвращается в штатный режим.

## API ESP32

- `GET /` — веб-интерфейс
- `GET /state` — текущее состояние
- `GET /settings` — текущие настройки
- `POST /set?param=...&value=...` — изменить параметр
- `POST /action?pump=well|house&cmd=...` — команды (`reset_alarm`, `force_on`, `force_off`)
- `GET /logs_well`, `GET /logs_house`
- `POST /clear_logs_well`, `POST /clear_logs_house`

## Wi‑Fi

ESP32 работает в режиме **AP + STA**:
- AP: `Nasos-ESP32` / `12345678`
- STA: `wifi_ssid` / `wifi_pass` в настройках

Если роутер недоступен, интерфейс доступен через AP ESP32 по адресу `192.168.4.1`.



## Калибровка тока VFD

Ток частотника для защит теперь читается ESP32 напрямую по Modbus RTU (через MAX485).
Аналоговый канал `PIN_CURRENT` на Nano оставлен как вспомогательная телеметрия (`analogAuxRaw`) для диагностики.

## Диагностика I2C отдельно от логики насосов

Добавлены минимальные диагностические скетчи:
- `diagnostics/esp32_i2c_probe.ino` — сканер + целевой probe адреса Nano.
- `diagnostics/nano_min_i2c_slave.ino` — минимальный Nano slave-ответчик.

Рекомендуемый порядок:
1. Залить в Nano `diagnostics/nano_min_i2c_slave.ino`.
2. Залить в ESP32 `diagnostics/esp32_i2c_probe.ino`.
3. Проверить в Serial, что есть ACK на адресе из `i2c_link_config.h`.
4. После подтверждения шины вернуть рабочие `v1.ino` и `esp32_controller.ino`.



## Примечание по Nano setup()

В `v1.ino` инициализация I2C (`Wire.begin(slaveAddress)`) выполняется в самом начале `setup()`, до длительных операций (например, калибровка АЦП), а в Serial добавлены явные boot-логи и heartbeat. Это упрощает разделение причин: Nano не стартует, не входит в slave-режим, или уже проблема шины/протокола.



## Примечание по миграции VFD

Начиная с версии протокола `v3`, Nano больше не содержит RS-485/Modbus логики VFD и не принимает команды RUN/FREQ по I2C. Все команды VFD (RUN/STOP/частота) и чтение токов/статуса выполняются на ESP32.
